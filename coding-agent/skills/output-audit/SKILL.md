# Output Audit

今回の作業で作成・変更した成果物を、将来の保守性、読みやすさ、再利用性の観点で監査する。対象はコード、設定、文書、生成物、および利用者に返す回答とする。実装の仕様適合性・脆弱性・テスト網羅性はこのスキルの対象外であり、必要なら別のレビューとして扱う。

## 監査の進め方

1. 変更差分と、その周辺の既存実装・既存文書を確認する。差分だけで判断できない場合は、同じ責務を持つ箇所を検索して比較する。
2. 各観点について、問題の有無を根拠とともに判定する。明確な根拠がない推測は指摘にしない。
3. 問題があれば、影響範囲を最小に保つ具体的な改善案を示す。監査だけを依頼された場合は、成果物を変更しない。

## 判定基準

### 局所最適化による負債

今回の変更だけを成立させるために、既存の抽象化、命名、データモデル、拡張経路、運用方法を不自然に迂回・例外化していないかを確認する。

- 同種の将来変更で同じ特例を増やす必要がある、または既存の共通機構を使えず分岐が増える場合は問題とする。
- 要求に固有の制約であり、境界が明確で将来の拡張を阻害しない場合は問題としない。
- 改善案では、過剰な一般化を避け、共通化・責務の配置・境界の明確化のうち必要なものだけを提案する。

### 重複

同じ意味・同じ判断・同じ値・同じ説明が複数箇所で独立して管理されていないかを確認する。表記が違っても、変更時に複数箇所を同期する必要があるなら重複として扱う。

- 重複した実装、定数、設定、手順、説明を検索して確認する。
- 意図的な冗長化が可用性、可読性、外部形式、または独立性のために必要な場合は、その理由を確認し問題にしない。
- 改善案では、単一の定義元、共通部品、参照、または削除のうち最も小さい変更を選ぶ。

### 過度な装飾

内容の理解や操作に寄与しない視覚的・文章的な装飾が、情報の優先順位を損なっていないかを確認する。

- 不必要に多い見出し、強調、絵文字、罫線、色、バッジ、キャッチコピー、凝った表現を確認する。
- 注意喚起、操作性、アクセシビリティ、または既存デザインシステムに基づく装飾は問題としない。
- 改善案では、意味を持たない装飾だけを減らし、重要な区別は残す。

### 過度な冗長さ

同じ結論の言い換え、前提の繰り返し、判断に不要な経緯、過剰な手順や例が、読者の理解を遅らせていないかを確認する。

- 読者が目的、結論、実行すべきことを把握するために不要な部分を特定する。
- 安全上の注意、意思決定の根拠、再現に必要な条件、または利用者が求めた詳細は削らない。
- 改善案では、削除・統合・短文化のどれで意味を保てるかを示す。

### 過渡的・ハイコンテキストな記述

作業中だけ通じる仮名、暫定事情、会話の前提、個人の記憶、暗黙の手順に依存し、第三者が単独で読んでも意味を復元できない記述が残っていないかを確認する。

- 「これ」「あれ」「前の対応」「いつもの方法」のように対象や条件を特定できない表現、理由のない一時的な値、説明のない略語を確認する。
- 短期的な措置が必要な場合は、恒久化の条件・期限・追跡先のいずれかを明示できているかを確認する。
- 改善案では、具体的な対象・条件・理由・参照先を補うか、不要な暫定記述を削除する。

## 報告形式

先に監査対象と結論を一文で示す。指摘がない場合は、各観点を確認したことと、問題なしと判断した根拠を簡潔に報告する。指摘がある場合は、重要度の高い順に次を記載する。

- 観点
- 対象箇所
- 根拠と将来の影響
- 最小限の改善案

曖昧な懸念を問題として列挙しない。成果物の性質上、判断できない観点がある場合は、未確認の理由と、確認に必要な情報を明示する。
