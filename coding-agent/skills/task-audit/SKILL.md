# Task Audit

完了した作業が要求を満たし、未完了や品質上の妥協を残していないかを厳密に監査する。監査では、確認できた事実だけを根拠にする。

## 監査手順

1. 元の依頼と受入条件を確認し、各要件が正しく理解され、すべて充足しているかを検証する。
2. 変更内容と関連箇所を確認し、部分実装、TODO、プレースホルダー、暫定対応、将来対応への先送り、未解決の技術的負債を探す。
3. 実装品質を確認する。ショートカットや不必要な妥協、エラー処理の不足、考慮されていない境界条件を確認する。
4. テストの実施内容と対象範囲を確認し、不足がある場合は根拠とともに報告する。正当な理由がないテスト欠落は品質上の問題として扱う。
5. 変更に必要な文書・設定・利用手順が更新されているかを確認する。
6. リポジトリ内の規約、スタイルガイド、貢献手順、検証要件を確認し、変更がすべて従っているかを検証する。

## 判定基準

- すべての要件が根拠をもって確認でき、未解決の必須事項がなければ Pass とする。
- 要件未充足、未完了、暫定対応の放置、品質・テスト・文書・規約上の問題があれば Fail とする。
- 確認に必要な情報が不足している場合は、未確認の理由と必要な情報を明示し、根拠なく Pass としない。
- 指摘は重大度順に整理し、各項目に具体的な `file:line`、影響、修正方法を記載する。

## 報告形式

```markdown
# Task Audit Report

## 要件充足
[Pass/Fail] - [確認した要件と根拠]

## 完了状況
[Pass/Fail] - [未完了、TODO、暫定対応、先送りの確認結果]

## 品質・テスト・文書
[Pass/Fail] - [品質、テスト、文書の確認結果]

## リポジトリ規約
[Pass/Fail] - [確認した規約と適合状況]

## 要修正事項
1. [重大度] [内容] - [file:line] - [影響] - [修正方法]

## 総合判定
[Pass/Fail] - [結論]
```

指摘がない場合も、各項目を確認した根拠を簡潔に記載する。曖昧な懸念を問題として列挙しない。
